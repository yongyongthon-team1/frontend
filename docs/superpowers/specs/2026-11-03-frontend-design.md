## 1. 무엇을, 왜

**서비스.** 용인에는 대학이 5곳(강남대 · 경희대 국제캠 · 단국대 죽전 · 명지대 자연캠 · 한국외대 글로벌캠)이고, 방학이면 대학가 상권의 손님이 크게 준다. 이 서비스는 **진로를 탐색하는 고교생**과 **재학생 가이드**를 캠퍼스 탐방으로 연결하고, 탐방 코스에 **대학가 제휴 상점**을 넣어 쿠폰 · 리뷰로 방학 상권에 사람을 보낸다. AI는 ① 고교생의 문장에서 관심사를 뽑아 탐방을 추천(T-01) ② 승인된 신청자들의 "하고 싶은 것"으로 코스 초안을 생성(C-01) ③ 상점 리뷰를 요약(R-03)한다. 공공데이터는 캠퍼스 · 방학 기간 · 상점(인허가 데이터) · 사업자 진위확인에 쓴다.

**이 프론트엔드가 하는 일.** 4개 역할(고교생 · 대학생 가이드 · 사장님 · 운영자)의 모든 사용자 흐름을 담는 **모바일 웹 앱**. 2026-11-15 해커톤 본선에서 **행사장 노트북으로 2분 라이브 시연**을 하고, 배포 링크와 GitHub 레포를 제출해 심사받는다.

**왜 이렇게 만드나.** 심사 5항목(각 20점) 중 프론트가 직접 좌우하는 건 **기술 구현**("핵심 기능이 안정적으로 동작하는가")과 **디자인 & UX**("처음 봐도 이해되는 흐름인가", "AI · 데이터 결과를 이해하기 쉽게 보여주는가")다. AI · 데이터 항목도 화면에 보여야 점수가 된다. 그래서 이 설계는 **(1) 2분 안에 끊김 없이 이야기를 보여주는 것 (2) 백엔드 · 디자인이 늦어도 멈추지 않는 것 (3) AI · 데이터가 눈에 보이는 것**을 기준으로 결정했다.

## 2. 목표 · 비목표 · 안티 목표

### 목표
- 범위 안 화면 전부(5.3)를 와이어프레임 흐름대로 구현. 모바일 390px 기준.
- 백엔드 명세 전에는 **ERD 모양을 따르는 목업**으로 개발하고, 명세가 오면 **도메인 단위로 실서버에 갈아끼운다**.
- **시연 지원 도구**: 역할 빠른 전환, 시연 데이터 초기화, 원클릭 시연 링크, 발표 모드.
- **하이파이 시안이 오면 토큰 · 컴포넌트 교체만으로 반영**되는 스타일 구조.
- **진척 확인 문서** 운영 **[사용자]**.

### 비목표
- 네이티브 앱, 서버 렌더링 · SEO, Next.js.
- 백엔드 로직 자체(LLM 호출, 쿠폰 발급, 진위확인 API, 이메일 발송). 프론트는 결과를 보여주고, 목업은 그 동작을 흉내만 낸다.
- 빈 시간 달력, 상점 우선순위 점수(D-02 삭제), D-03(정의 없음).
- 다국어, 다크 모드, 푸시 알림, 결제.

### 안티 목표 (돌아가더라도 이러면 실패)
- 시연 2분 중 로그인 · 역할 전환 · 입력 · 데이터 준비에 시간을 쓰는 구조.
- 백엔드 명세가 늦다고 프론트가 멈추거나, 명세가 오면 화면 코드를 갈아엎어야 하는 구조.
- 하이파이 시안이 왔을 때 화면을 처음부터 다시 짜야 하는 스타일 구조.
- AI 결과가 "그냥 목록"처럼 보여서 AI를 썼는지 티가 안 나는 것. AI 설명 문구가 실제 기준과 다른 것.
- 본선 날 백엔드 · 지도 SDK · 네트워크 · 지난 리허설의 데이터 중 하나 때문에 시연이 멈추는 것.
- 무대 노트북 화면에서 핵심 정보(AI 키워드 · 이유, 코스 지점, 쿠폰 코드)가 접혀서 안 보이는 것.
- 비활성 버튼만 있고 "왜 안 되는지 · 어떻게 하면 되는지"가 없는 화면.

## 5. 설계

### 5.1 기술 스택 [제 판단 — "보편적인 방식" 기준]

| 영역 | 선택 | 이유 |
|---|---|---|
| 빌드 | Vite + React 19 + TypeScript(strict) | SPA 표준 조합 |
| 라우팅 | React Router **7** (data router, `createBrowserRouter`) | 가장 널리 쓰임 |
| 서버 상태 | TanStack Query **5** | 캐시 · 무효화 · 로딩/에러 상태 표준 |
| 클라이언트 상태 | Zustand (세션 토큰 · 시연 설정, localStorage persist) | 작고 흔함 |
| 폼 | React Hook Form + Zod | 검증 규칙을 스키마로 |
| 스타일 | Tailwind CSS **4** + CSS 변수 디자인 토큰, 접근성 프리미티브는 shadcn/ui(Radix) | 하이파이 반영을 토큰 교체로 |
| 아이콘 · 폰트 | lucide-react · Pretendard(**직접 호스팅** woff2) | 외부 CDN 의존 없음 |
| 지도 | 카카오맵 JavaScript SDK + 도식 지도 폴백 | 국내 사용자 · 심사위원에게 익숙 |
| 목업 | MSW **2** + 인메모리 DB(localStorage 보존, 이미지는 IndexedDB) | 브라우저 · 테스트 양쪽에서 같은 핸들러 |
| 날짜 | date-fns (ko), 표시 타임존 Asia/Seoul | |
| 테스트 | Vitest + Testing Library + MSW(node), Playwright | |
| 품질 | ESLint(flat) + Prettier, GitHub Actions(typecheck · lint · test · build) | |
| 패키지 매니저 | npm, **lockfile 커밋** | 팀원 누구나 추가 설치 없이 |
| 배포 | Vercel (SPA rewrite + `/api` 프록시 rewrite) | |

- **메이저 버전을 위 표대로 고정**한다(설치 시점에 더 새 메이저가 있어도 표의 메이저 안에서 최신). 11/8 이후에는 의존성을 올리지 않는다.
- **라우트 단위 코드 분할(lazy)을 하지 않는다.** 화면 40개 규모에선 이득이 작고, 무대에서 역할을 바꿀 때 청크 로딩 실패 · 재배포 후 옛 청크 요청 오류가 시연을 멈출 수 있다. 번들이 커지면 첫 화면 뒤 전체 프리로드 + `vite:preloadError` 시 새로고침으로 대응한다.

### 5.2 폴더 구조 [제 판단]

```
src/
  app/          엔트리, Providers, router, 레이아웃(MobileFrame · 역할별 TabLayout), 가드, 에러 경계
  pages/        라우트 화면 — auth/, student/, guide/, owner/, admin/, public/(보호자 동의)
  features/     도메인 모듈 — auth, verification, campuses, tours, applications, courses,
                stores, coupons, reviews
                  각 모듈: api.ts(요청 함수 · DTO · 변환) / queries.ts(TanStack 훅 · query key) /
                           model.ts(타입 · 상태 라벨 · 표시 상태 파생 함수) / components/
  shared/       ui/(디자인 시스템 컴포넌트), lib/(http 클라이언트 · format · date), config/(env), hooks/
  demo/         시연 패널, 원클릭 시연 링크 처리, 발표 모드
  mocks/        db/(스키마 · 시드), rules/(업무 규칙 순수 함수), ai/(AI 흉내), handlers/(도메인별),
                browser.ts, node.ts
  styles/       tokens.css, globals.css, fonts/
docs/           reference/, superpowers/specs · plans/, progress/, decisions/, api/
```

**규칙**: 화면(pages)은 `features/*/queries.ts`의 훅만 쓴다. HTTP · DTO는 `features/*/api.ts` 안에만 있다. 백엔드 명세가 오면 고칠 곳이 `api.ts`(와 목업 핸들러)로 한정된다.

### 5.3 화면 맵 · 라우트 · 우선순위

우선순위: **P0** = 시연 골든 패스(11/8까지 목업으로 완동, 다듬기 우선) · **P1** = 나머지 MVP(11/8까지 막다른 곳 없는 최소판) · **P2** = 11/10 체크포인트 통과 후 · **OUT** = 만들지 않음. 화면 코드는 [`wireframes.md`](../../reference/wireframes.md) 기준. 라우트 이름은 [제 판단]이고 빌더가 조정 가능. **11/6 시연 대본이 확정되면 P0를 대본 화면 기준으로 다시 맞춘다.**

### 5.4 로그인 후 이동 · 권한 · 세션 [기능 명세 U-02 + 제 판단]

- **가드 두 겹**: ① 로그인 필요(`RequireAuth` → `/login?next=`) ② 역할 일치(`RequireRole` → 내 역할 첫 화면으로).
- **인증 미완료는 화면을 막지 않고 동작을 막는다.** 인증 전에도 홈 · 탐방 목록은 볼 수 있다. 신청 · 개설 · 가게 연결 버튼은 비활성 + **사유와 다음 행동**을 함께 보여준다.
- **첫 화면**
  - 고교생: 할 일이 있으면 `/verify` — 재학 인증 미제출 · 반려, 보호자 동의 미요청 · 거부 · 링크 만료. 없으면(심사 중 · 동의 대기 포함) `/`.
  - 가이드: 재학 인증 미제출 · 반려면 `/guide/verify`, 가이드 프로필(학과) 미작성이면 `/guide/me`, 아니면 `/guide/tours`.
  - 사장님: 사업자 미인증이면 `/owner/verify`, 가게 미연결이면 `/owner/store/connect`, 아니면 `/owner/store`.
  - 운영자: `/admin/verifications`.
- **`/verify` 단계 카드**: STEP1 재학 인증 = 미제출 폼 / 심사 중 / 반려 사유 + 재제출 / 승인. STEP2 보호자 동의 = 미요청 폼 / 동의 대기(재발송) / 거부 · 만료(재요청) / 동의 완료. 두 단계는 따로 제출한다. `/guide/verify`도 STEP1과 같은 상태를 갖는다.
- **세션**: 토큰은 Zustand persist(localStorage), 사용자 · 인증 요약은 TanStack 쿼리(`['me']`)로 두고 화면 진입 · 창 포커스 때 다시 불러온다(운영자 승인 · 보호자 동의가 다시 로그인하지 않아도 반영). **로그인 · 로그아웃 · 역할 전환 때 쿼리 캐시를 통째로 비운다**(이전 역할 데이터가 잠깐 보이는 문제 방지).
- 토큰은 `Authorization: Bearer`로 보낸다(백엔드가 쿠키 세션을 택하면 http 클라이언트 한 곳만 바꾼다). 401이면 세션을 지우고 `/login`으로. **단, 시연 계정으로 빠른 전환한 상태면 한 번 자동 재로그인**한 뒤 실패할 때만 `/login`.

### 5.5 데이터 · API 연동 계층

**도메인 타입.** ERD를 따라 TypeScript 타입을 직접 쓴다. 상태값은 ERD enum 그대로 쓰고, 한국어 라벨과 **표시 상태 파생 함수**는 `model.ts`에 둔다(단위 테스트 대상).

| 대상 | 값 → 라벨 |
|---|---|
| 탐방 | RECRUITING 모집 중 · CLOSED 마감 · CANCELED 취소 · COMPLETED 완료 |
| 신청 | PENDING 승인 대기 · APPROVED 승인 · REJECTED 거절 · CANCELED 취소 |
| 재학 인증 | (없음) 미제출 · PENDING 심사 중 · APPROVED 승인 · REJECTED 반려 |
| 보호자 동의 | (없음) 미요청 · PENDING 동의 대기 · AGREED 동의 완료 · REJECTED 거부 · (expires_at 지남) 링크 만료 |
| 코스 — 가이드 화면 | (없음) 코스 없음 · DRAFT 초안 · CONFIRMED 확정 |
| 코스 — 고교생 화면 | (없음) · DRAFT → **준비 중**(지도 · 쿠폰 진입 막음) · CONFIRMED → 확정 |
| 쿠폰 (표시 상태) | ISSUED + 탐방일 전 → "탐방 당일 사용 가능" · ISSUED + 당일 → "사용 가능" · ISSUED + expires_at 지남 또는 EXPIRED → "만료" · USED → "사용 완료 · 사용 시각" |

- **내 탐방 표시 상태**(hs-a05 카드): 신청 × 탐방 × 코스 상태를 합쳐 문구와 다음 행동을 정하는 함수 하나로 만든다. 예: PENDING → "승인 대기 · 승인 전 직접 취소 가능" / APPROVED + 코스 없음·DRAFT → "승인 · 코스 준비 중" / APPROVED + CONFIRMED → "코스 확정 · 지도와 쿠폰 보기" / APPROVED + 탐방 COMPLETED → "탐방 완료 · 리뷰 쓰기" / REJECTED → "거절 · 다른 탐방 보기" / CANCELED 또는 탐방 CANCELED → "취소 · 쿠폰 만료".
- **날짜 · 시각 판단의 주인**: 실서버 모드에서 프론트는 자기 시계로 유효 여부를 판단하지 않고, **서버가 준 상태 · 가능 여부 플래그**를 그린다. 쿠폰 표시 파생은 목업 모드와 서버가 플래그를 안 줄 때만 쓴다. 날짜는 `+09:00` 오프셋이 붙은 ISO 8601로 주고받는다(백엔드와 합의 — 5.5 끝 계약 초안).

**HTTP 클라이언트.** `fetch` 래퍼 하나:
- base URL(`VITE_API_BASE_URL`, 기본 `/api`), JSON, 토큰 헤더, **multipart(FormData) 업로드 경로**(학생증 사진).
- 타임아웃: 기본 15초, AI 엔드포인트(T-01 · C-01) 30초 → 오류 상태 + 다시 시도.
- 에러 정규화 `ApiError { status, code, message, fieldErrors?, details? }` — `details`로 "이미 사용된 쿠폰"의 사용 시각 같은 값을 받는다. 409는 "이미 처리됨" 계열로 다루고 목록을 다시 불러온다.
- 에러 `code` → 한국어 문구 매핑 표: 이메일 중복 · 형식 오류, 비밀번호 불일치, 인증 전 · 동의 전, 정원 마감, 중복 신청, 탐방 날짜 이후 취소 불가, 완료된 탐방 취소 불가, 정원 초과 승인, 승인 0명 코스 생성 불가, 확정 후 수정 불가, 지점 0개 확정 불가, 방학 밖 날짜, 필수 값 누락, 가이드 프로필 미작성, 사업자 정보 불일치 · 휴폐업, 이미 연결된 가게 · 계정당 1개, 제휴 기간 오류, 쿠폰 다른 가게 · 이미 사용 · 만료 · 없는 코드, 쿠폰 미사용 리뷰 · 중복 리뷰, 이미 처리된 심사 요청, 이미지 형식 · 용량 오류, 동의 링크 만료 · 무효.

**서버 상태.** 도메인별 query key 팩토리. 변경 후 무효화 규칙을 한곳에 적는다(예: 신청 승인 → 탐방 상세 · 신청자 목록 · 내 탐방 · 내가 개설한 탐방). 쿠폰 상세는 ISSUED인 동안 5초 간격으로 다시 불러와 사장님이 사용 처리하면 화면이 바뀌게 한다.

**업무 규칙의 최종 기준은 백엔드 API다.** 기획자 메모(10/30, `docs/reference/feature-spec.md` 맨 아래)에 따르면 명세의 "처리 · 규칙"은 형식적으로 잡은 것이고 백엔드가 구현 방식에 따라 바꿔도 된다. 그래서 아래 목업 규칙은 명세를 따른 **잠정안**이고, API 명세가 오면 백엔드 동작에 맞춘다. 문서 간 불일치를 처리한 원칙과 20건의 처리 내역은 [`docs/reference/README.md`](../../reference/README.md)에 있다.

**목업(MSW).**
- **범위**: 골든 패스 경로와 화면에 보일 예외 상태의 규칙만 구현한다. 백엔드가 어차피 만들 내부 규칙을 전부 복제하지 않는다.
- `mocks/db`: ERD 테이블을 본뜬 인메모리 DB. 시드 = 5개교(대략의 실제 좌표 · 행정동 · 방학 기간), 캠퍼스 장소, 캠퍼스별 가상 상점 6~10곳(실제 상호 사용 안 함), 제휴 할인, 역할별 시연 계정, 여러 상태의 탐방 · 신청 · 코스 · 쿠폰 · 리뷰 · 요약. **시연 탐방 날짜 · 제휴 기간은 시드를 만드는(초기화하는) 날을 기준으로 한 상대 날짜**로 넣는다 — 시연 탐방은 "오늘", 시작 시각은 발표 시간대 이후, 제휴 기간은 오늘을 포함(4장 결정). 시드는 검증 규칙(방학 기간)을 거치지 않고 직접 넣는다.
- **골든 패스 시드 보장**: C-01 규칙(관련 후보 중 제휴 상점 최소 1곳 포함, 4장 결정)에 더해, 시연 캠퍼스 주변의 식사 · 카페 상점은 모두 제휴 상점으로 두고 제휴 상점마다 사장님 시연 계정을 둔다. 그래서 어떤 제휴 가게가 뽑혀도 "쿠폰 가게 사장님으로 전환"(5.8)으로 이어진다. Playwright 골든 패스에서 쿠폰 발급 · 사용을 단언한다.
- **체크포인트 시드**: "신청 완료" · "승인 완료" · "코스 확정" · "쿠폰 발급" 단계에서 바로 시작할 수 있는 시드를 둔다(시연 중 문제가 생기면 그 단계부터 이어 간다).
- `mocks/rules` (순수 함수, 쿠폰 · 정원 · 날짜 · 시간 슬롯 규칙은 단위 테스트):
  - 신청: 자격(재학 인증 APPROVED + 보호자 AGREED), RECRUITING · 남은 자리(정원 − 승인 수), **중복 = 같은 탐방에 PENDING 또는 APPROVED 신청이 있을 때**, 취소 이력이면 재신청 허용, 거절 이력이면 "거절됨" 표시 + 재신청 불가(9장), 탐방 날짜 전까지만 취소, 승인 취소 시 자리 복구(CLOSED → RECRUITING) · 쿠폰 만료.
  - 승인: 본인 탐방만, 정원 초과 승인 불가, 승인 수 = 정원이면 자동 CLOSED, 오픈채팅 링크는 APPROVED 신청자 응답에만 포함, 코스 확정 뒤 승인하면 그 신청자에게도 쿠폰 발급.
  - 탐방: 개설은 재학 인증 APPROVED + 가이드 프로필 작성 + 방학 기간 안 날짜, 완료된 탐방 취소 불가, 탐방 취소 시 모든 신청 CANCELED + 발급 쿠폰 EXPIRED, 완료 처리는 탐방 날짜 이후만.
  - 코스: 초안은 승인 ≥ 1, 수정은 DRAFT일 때만, 확정은 지점 ≥ 1, 확정 시 쿠폰 발급(승인자 × 코스 안 제휴 상점, 유효기간 = 탐방 당일, 제휴 0곳이면 발급 0장), 조회(C-04)는 CONFIRMED이고 요청자가 APPROVED 신청자나 해당 가이드일 때만. **방문 시간은 위치 슬롯에 고정**(탐방 시작 시각 + 슬롯 간격) — 순서를 바꾸면 지점만 옮기고, 추가 · 삭제 때 슬롯을 다시 계산한다. 시간 직접 수정은 없다(C-02에 없음).
  - 상점 · 쿠폰: 계정당 가게 1개, 다른 사장님이 연결한 가게 선택 불가, 제휴 기간 검증(시작 ≤ 종료), 사용 처리는 내 가게 쿠폰 · ISSUED · 유효기간 안일 때만.
  - 리뷰: 그 상점 쿠폰을 USED한 사람만, **ERD 기준 탐방 × 상점마다 1건**(쿠폰 1장당 1건, 9장).
  - 인증: 이미 처리된 심사 요청은 409, 심사가 끝나면 이미지 삭제(`document_url` 비움), 보호자 재요청 시 토큰 · expires_at 갱신하고 PENDING.
  - 사업자 인증: 시드한 데모 사업자번호 3종 = 일치(후보 상점 2곳) / 불일치 / 폐업.
  - 이미지 업로드: jpg · png · heic, 10MB 이하(클라이언트에서도 검증). 이미지는 IndexedDB(또는 메모리 object URL)에 두고 DB에는 참조만 저장해 localStorage 한도를 넘지 않게 한다.
- `mocks/ai`: AI 흉내. T-01 = 키워드 사전으로 관심사 추출 → **RECRUITING 탐방만 대상, 학교 · 날짜는 입력했을 때 필터** → 가이드 학과 · 소개와 매칭해 정렬 → 템플릿 추천 이유. 0건이면 학교를 골랐을 땐 그 학교의 모집 중 탐방, 안 골랐을 땐 전체 모집 중 탐방을 날짜 · 남은 자리 순으로 보여주고 "조건을 넓혀서 보여 드려요" 안내. C-01 = 승인자들의 "하고 싶은 것"에서 식사 · 카페 · 놀거리 의도를 뽑아 캠퍼스 장소 + 관련 업종 상점으로 2~3시간 코스와 이유 생성, **관련 후보 중 제휴 상점을 최소 1곳 포함**(4장 결정). R-03 = 리뷰 저장 시 템플릿 요약. **지연은 기본 1~2초, 시연 패널에서 "느리게(10초)"로 바꿀 수 있다. 출력은 일부러 들쭉날쭉하게**(긴 이유, 지점 4~5개, 리뷰 없는 상점)해서 레이아웃이 미리 버티게 한다.
- **보존**: DB를 localStorage에 버전 키로 저장 → 새로고침 · 역할 전환 후에도 시연 상태가 이어진다. "시연 데이터 초기화"로 시드 복원.
- **모드 전환**: `VITE_API_MODE=mock|real` + 런타임 전환(시연 패널 · 원클릭 링크, localStorage 저장). 연동 기간의 개발 편의로 `VITE_MOCK_DOMAINS`로 도메인 단위 목업을 켤 수 있다(목록에 없는 도메인은 MSW가 통과시켜 실서버로) — **단, 시연 · 리허설은 "전부 목업" 또는 "전부 실서버"로만 한다**(섞으면 ID · 상태가 어긋나 원인 모를 버그가 난다).
- **실서버 응답을 목업 픽스처로**: 11/13 리허설에서 시연 입력에 대한 실서버 응답(T-01 · C-01 · R-03)과 시연 캠퍼스 주변 실제 상점 데이터를 저장해 목업 시드로 쓴다. 폴백 시연에서도 실제 AI 출력과 실데이터를 보여주기 위해서다.

**백엔드 명세가 오면.** OpenAPI(Swagger)가 있으면 `openapi-typescript`로 타입을 생성해 DTO를 맞춘다. 응답 필드 표기 차이는 `api.ts`의 변환 함수에서 흡수한다. **연동은 시연 대본 순서대로** 도메인 하나씩 하고, 할 때마다 진척 문서의 API 연동표를 갱신한다.

**API 계약 초안 `docs/api/frontend-needs.md` [제 판단].** 목업 핸들러가 곧 "프론트가 기대하는 API"이므로 **11/5까지 골든 패스 엔드포인트(15~20개)를 계약 초안 수준**(메서드 · 경로 · 요청 · 응답 예시 · 에러 코드)으로 쓰고, 나머지 화면은 필요한 데이터 · 동작 목록으로 정리한다. 공통 규약 제안: 필드 표기, 에러 봉투 `{ code, message, fieldErrors, details }`와 코드 목록, `+09:00` ISO 8601, ID 타입, Bearer 토큰, 목록 응답 모양. 백엔드에 질문할 것: 표시용 집계 값을 응답에 포함할지(탐방 제목 = 대학교 + 가이드 학과, 남은 자리, 내 신청 상태, 가이드 인증 배지, 지점별 리뷰 요약 · 별점 · 제휴 여부, 쿠폰별 리뷰 작성 여부), 사진 업로드 방식(multipart / presigned URL), 직접 등록 가게의 주소 → 좌표 변환 주체, 코스 순서 변경 시 방문 시간 재계산 주체, LLM 결과 캐시 · 타임아웃 대체 응답. 사용자가 팀 채널에 공유해 백엔드와 30분 리뷰하고, **골든 패스 계약은 11/6까지 동결**하는 것을 제안한다.

### 5.6 AI · 데이터를 보여주는 방식 [제 판단, 심사 대응]

- AI가 만든 것에는 항상 같은 표식(✦ + "AI 추천" 등)을 붙이고, **왜 그런 결과인지 한 줄**을 함께 보여준다 — 추출된 관심 키워드 칩, 탐방별 추천 이유, 코스 지점별 추천 이유, 리뷰 요약.
- 코스 초안 화면은 **입력(승인된 신청자들의 관심사) → 결과(지점 · 시간 · 이유)**가 한 화면에서 이어지게 한다(guide-s04 구조).
- **와이어프레임의 옛 기준 문구를 실제 기준으로 바꾼다**: guide-s04 "추천 상점 기준: 지역 데이터 점수 · 제휴 여부 · 리뷰 요약" → "신청자들이 적은 하고 싶은 것 → 관련 업종 상점 매칭(인허가 공공데이터) · 제휴 상점 1곳 이상 포함", guide-s05 · guide-a03의 "우선순위 · 공공데이터 점수" 문구도 같이 바꾼다. 바뀐 문구는 디자인 · 기획에 공유한다. **주변 상점(S-02) 정렬은 "하고 싶은 것과 관련된 업종 우선, 그다음 거리순"**(D-02 삭제로 점수 정렬 불가).
- 데이터 출처 라벨: 상점 = "공공데이터(인허가) 기반", 캠퍼스 · 방학 기간 = "학사 일정 데이터" 등. 문구는 팀 데이터 담당과 맞춘다.
- **데이터 인사이트 자리**: 추천 목록 또는 코스 초안 상단에 "방학 상권 인사이트" 카드(예: "이 캠퍼스 행정동은 방학에 소비가 X% 줄어요 — 출처 · 연도"), 사장님 사용 처리 완료 화면에 "이번 탐방으로 온 학생 N명". 자리와 목업 값은 프론트가 먼저 만들고, 실제 지표는 팀 데이터 담당이 정한다(9장).
- AI 처리 중에는 스켈레톤 + 단계 문구("관심사를 분석하고 있어요" → "탐방을 비교하고 있어요"), 타임아웃 · 실패 시 다시 시도.
- 상점 바텀시트(코스 지도): 시간 · 추천 이유 · AI 리뷰 요약 · 별점 평균 · 리뷰 수 · 최근 리뷰(펼치기) · 제휴면 쿠폰 보기. 리뷰 0건이면 "아직 리뷰가 없어요".

### 5.7 디자인 시스템 · 하이파이 반영 [제 판단]

- 하이파이(11/6)가 오기 전에는 와이어프레임 레이아웃을 따르고(옛 기준 문구는 5.6대로 교체), **중립 테마**(Pretendard, 회색조 + 강조색 1개)로 시연 가능한 수준까지만 다듬는다.
- 모든 색 · 반경 · 간격 · 글자 크기 · 그림자는 `styles/tokens.css`의 CSS 변수로 정의하고 Tailwind 테마가 그 변수를 쓴다. 하이파이 반영 = 토큰 값 교체 → 컴포넌트 스타일 패스 → 화면 패스. **반영 순서는 골든 패스 화면부터.**
- 와이어프레임에서 뽑은 공통 컴포넌트: TopBar(68px) · BottomTabBar(81px) · Button(primary/secondary, 50px) · TextField(56px) · Textarea · StatusChip · InfoCard · TourCard · Badge(인증 배지) · StarRating · CodeInput(6자리) · StepCard · EmptyState · ErrorState · Skeleton · BottomSheet/Dialog · Toast. 좌우 여백 20px.
- **무대 화면 제약**: 무대 노트북에서 브라우저 UI를 뺀 실제 페이지 영역을 1366×620 · 1280×600 · 1280×590(배율 150%)으로 잡는다. 폰 프레임 높이가 min(844px, 화면 높이 − 32px)이므로, 여기서 TopBar(68px)와 하단 탭(81px)을 빼면 본문은 439 · 419 · 409px뿐이다. 골든 패스 화면은 핵심(AI 키워드 · 이유, 코스 지점, 쿠폰 코드)이 본문 상단 약 400px 안, 하단 탭 위에 보이게 배치한다(판정 28 — 처음 잡은 450px은 이 뷰포트에서 맞지 않아 줄였다). 세 뷰포트 모두 `e2e/stage-viewport.spec.ts`로 확인한다. 이 제약을 디자이너에게도 전한다.
- 디자이너에게 요청(사용자가 전달): 토큰(색 · 글꼴 · 반경 · 그림자)은 11/5에 먼저, 화면은 골든 패스부터, 11/6 이후에는 흐름 · 정보 구조 변경 없음, 변수 · 컴포넌트가 있는 피그마 **디자인 파일**로 전달. 오면 Figma MCP로 변수 · 컴포넌트를 읽어 토큰에 매핑한다.

### 5.8 데스크톱 · 시연 레이아웃과 시연 도구 [제안·확인 + 제 판단]

- 뷰포트 폭 480px 미만: 전체 화면 모바일. 이상: 가운데 **폰 프레임(폭 390px, 높이 = 화면 높이 − 여백, 최대 844px)**, 프레임 안에서 스크롤. `transform: scale`은 쓰지 않는다(지도 클릭 · 드래그 좌표가 어긋남). 브라우저 줌 125~150%에서도 프레임이 화면 높이를 채우게 한다.
- **시연 패널**(프레임 옆, `VITE_DEMO_TOOLS=true` 또는 `?demo=1`일 때만): 역할 빠른 전환(시연 계정 즉시 로그인), **"방금 발급된 쿠폰의 가게 사장님으로 전환"**, **최근 발급 쿠폰 코드 표시**, 시연 데이터 초기화(목업은 시드 복원, 실서버는 백엔드 시연 리셋 수단 호출 — 4장 결정), 체크포인트 시드로 이동(목업), 현재 API 모드 표시 · 전환, 백엔드 헬스 표시, 지도 "도식 모드" 수동 토글, 목업 AI 속도.
- **발표 모드**(`?present=1`): 시연 패널을 작은 역할 전환기로 줄이고, 상단에 역할 배지 · 색으로 "지금 가이드 화면"임을 크게 보여준다.
- **원클릭 시연 링크**: `?demo=1&mode=mock|real&reset=1&as=student&present=1` 한 번으로 모드 · 초기화 · 역할 · 발표 모드를 세팅한다. 실서버 초기화는 비밀 키가 있을 때만 동작. 링크는 QR · 단축 URL로 준비한다.
- **입력 시간 줄이기**: 홈 추천 문장은 예시 칩 한 번 탭으로 채운다(hs-s03의 예시 문장), 시연 모드에선 신청서 문장을 미리 채운다, Enter 제출에는 한글 조합 중(`isComposing`) 가드, 사장님 6자리 입력란에 "최근 쿠폰 채우기" 버튼(시연 모드만).
- 시연 계정 정보는 환경변수로 넣는다(번들에 노출되므로 시연 전용 계정만). 실서버 모드의 빠른 전환은 백엔드가 같은 시연 계정을 시드해야 동작한다.
- Playwright로 5.7의 무대 뷰포트 세 개(1366×620 · 1280×600 · 1280×590 배율 150%)에서 스크린샷을 찍어 무대 화면을 점검한다.

### 5.9 지도 [제 판단]

- `MapView` 하나로 감싼다: 번호 핀(순서), 지점 간 선(선택), 핀 탭 → 상점 바텀시트(5.6).
- **폴백**: 키가 없거나, SDK 로딩이 4초 안에 안 끝나거나, `kakao.maps` 객체가 없으면 도식 지도 + 지점 리스트로 자동 전환. 시연 패널에 수동 토글도 둔다.
- 카카오에는 **고정 프로덕션 도메인과 localhost만** 등록한다(Vercel 프리뷰 URL은 배포마다 바뀌므로 거기선 폴백이 보이는 게 정상). 지도 검증 · 시연 · 제출은 고정 도메인으로만 한다.
- 직접 등록 가게의 좌표: 백엔드가 변환하지 않으면 카카오 SDK services(주소 검색)로 프론트가 변환한다. 목업은 캠퍼스 근처 좌표를 넣는다.
- 준비물(사용자/팀): 카카오 디벨로퍼스 앱의 JavaScript 키, 허용 도메인 등록.

### 6.1 골든 패스 (P0) [제 판단 — 실제 대본은 팀이 11/6까지 정함]

1. **고교생**: 홈에서 예시 칩으로 "산업디자인을 공부하고 싶고, 학생들이 주로 어디서 밥 먹는지 궁금해요" 입력 → **AI 추천 목록**(키워드 칩 · 추천 이유 · 남은 자리) → 탐방 상세 → 신청서(미리 채움) → 신청 완료.
2. **가이드로 전환**: 신청자 관리에서 승인 → **AI 코스 만들기**(신청자 관심사 → 지점별 이유) → 편집(위/아래 버튼으로 순서 1회) → 코스 확정 → 쿠폰 발급 결과.

5. (여유 시) 고교생 리뷰 작성 → AI 요약 갱신.

2분(앱 조작 90초 + 여유 30초) 안에 끝나도록 시드한다(가이드 · 탐방 · 다른 승인자 · 상점 · 제휴가 이미 있음). 대본이 정해지면 대본에 없는 화면은 P0에서 내린다.

## 7. 진척 관리 문서 [사용자 요청 → 범위 · 운영 방식은 제 판단]

**프론트엔드 진척 기준**으로 레포 안 Markdown에 둔다. 코드와 같이 버전 관리되고, GitHub에서 팀원 누구나 볼 수 있다. 팀 공식 일정은 노션 [`# 일정`](https://app.notion.com/p/408e0c1995d680e8be5cce86f42d362d)이 정본이다. 대시보드의 체크포인트 표는 그 일정에 맞추고 링크를 건다. 이 환경의 노션 연동은 팀 워크스페이스 권한이 없어(404) 노션에 직접 쓸 수 없다. 브라우저 자동화로는 쓸 수 있지만 불안정하다. 그래서 노션 보드의 상태(예: `개발 1차 (MVP)` → In progress)는 사용자가 요청할 때만 갱신한다. 팀 공유용 웹 페이지가 필요하면 요청을 받아 대시보드를 페이지로 띄운다.

| 문서 | 내용 | 갱신 시점 |
|---|---|---|
| `docs/progress/README.md` — **진척 대시보드** | ① **체크포인트 표**(1장 표 그대로, 상태 표시) ② **화면 진척표**: 화면 코드 · 화면 · 라우트 · 우선순위 · 단계(UI → 목업 연동 → 실API 연동 → 하이파이 반영 → QA) ③ **API 연동표**: 도메인/엔드포인트 · 계약 합의 · 목업 · 실서버 · 배포 URL에서 확인 ④ **팀 요청 · 블로커**: 백엔드 · 디자인 · 운영진에 필요한 것, 담당 · 기한 ⑤ 열린 질문 | 작업 단위가 끝날 때마다 해당 행 |
| `docs/progress/devlog.md` — **개발 일지** | 날짜별: 한 일 · 다음 할 일 · 이슈 | 작업 세션이 끝날 때 |
| `docs/decisions/NNNN-*.md` — **결정 기록** | 단일 SPA, 목업 선개발, 토큰 스타일, 지도 폴백, `/api` 프록시, lazy 미사용, 시연 날짜 처리 등 맥락 · 결정 · 결과 | 결정이 생길 때 |

- 구현 계획의 모든 태스크 마지막 단계에 "진척 문서 갱신"을 넣는다.
- 팀 요청은 레포 문서에만 두지 않는다. 사용자가 팀 채널(노션 · 단톡)에 올리고 레포 문서에는 링크로 연결한다.
