## 문서끼리 어긋난 점과 처리 (2026-11-04 기준)

### 처리 원칙

1. **나중에 정한 것이 우선한다.** `기능 명세 변경 정리`가 명세 본문 · 유저 플로우 · 와이어프레임보다 앞선다. 와이어프레임은 변경 전에 그려졌다.
2. **데이터 모양은 ERD를 따른다.** 백엔드가 ERD로 API 명세를 쓴다.
3. **업무 규칙의 최종 기준은 백엔드 API다.** 기획자 메모(10/30): 명세의 "처리 · 규칙"은 형식적으로 잡은 것이라 백엔드가 구현 방식에 따라 바꿔도 된다. 프론트 목업은 명세대로 잠정 구현하고, API 명세가 오면 거기에 맞춘다.
4. **시연 흐름이 끊기지 않는 쪽을 고른다.**
5. **문서만으로 정할 수 없는 것은 팀 확인으로 남긴다.** 진척 대시보드의 "팀 요청 · 블로커"에서 추적한다.

### B. ERD ↔ 명세 · 와이어프레임

| # | 어긋난 점 | 처리 | 팀 확인 |
|---|---|---|---|
| B1 | **회원가입 이름**: ERD는 `users.name` 필수인데 U-01 입력(이메일 · 비밀번호 · 역할)에 이름이 없음. 신청자 목록(A-04)은 이름을 보여줌 | 회원가입에 **이름 칸 추가** | — |
| B2 | **탐방 제목 · 학과 컬럼이 ERD에 없음** (화면엔 "경희대 국제캠퍼스 디자인 전공 탐방") | **"대학교 + 가이드 학과"**로 만들고 날짜를 함께 표시(같은 가이드의 탐방 구분) | 필요 — 탐방 개설에 제목 필드를 넣을지 |
| B3 | **가이드 학년**(와이어 "산업디자인학과 2학년")이 ERD에 없음 | 표시하지 않음(필드가 생기면 표시) | — |
| B4 | ERD **`tour_wishes`(희망 탐방)**에 대응하는 기능 · 화면이 없음 | **만들지 않음.** 홈 AI 추천 입력(T-01) 기록용으로 추정 | 필요 — 용도 확인 |
| B5 | **재신청**: ERD(`active_user_id`)는 거절 · 취소 뒤 다시 신청할 수 있는 구조인데 명세는 "중복 신청 차단"만 있음 | 취소한 탐방은 재신청 허용, **거절된 탐방은 재신청 불가**("거절됨" 표시) | 필요 |
| B6 | ERD `course_stops.partnership_id`의 참조 표기(`store_partnerships.partnership_id`)가 실제 PK(`id`)와 다름 | 프론트 영향 없음 — API 명세를 따름 | 백엔드 참고 |
